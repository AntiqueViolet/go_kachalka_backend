# go_kachalka backend — сервис авторизации (фаза 1)

Дата: 2026-10-22
Статус: согласована; 2026-10-23 уточнена по итогам проверки реализации (раздел 19)

## 1. Контекст и цель

Мобильное приложение (трекер тренировок) работает офлайн: данные пользователя лежат в локальной БД на устройстве. Нужен сервер на Go, который ведёт учётные записи и проверяет авторизацию. Сервер — единственный источник истины об учётных данных: клиенту не доверяем ничего, кроме того, что подписано сервером.

Фаза 1 — только авторизация. Фаза 2 (синхронизация данных) в этот документ не входит, но решения ниже не должны ей мешать.

Результат сдачи — полный комплект для развёртывания на своём сервере. Разработка и проверка — локально (Windows, Docker).

## 2. Ключевые решения

| Вопрос | Решение |
|---|---|
| Логин | Номер телефона + пароль |
| Подтверждение телефона | SMS-код при регистрации (номер без подтверждения занять нельзя) |
| Email | Обязателен при регистрации, подтверждается 6-значным кодом из письма |
| Вход без подтверждённого email | Разрешён; сброс пароля возможен только на подтверждённый email |
| Сброс пароля | 6-значный код на подтверждённый email |
| Гостевой режим | Есть на клиенте; серверу в фазе 1 ничего не нужно |
| SMS-провайдер | Интерфейс + заглушка, пишущая коды в лог; реальный адаптер — вне фазы 1 |
| Почта | SMTP (любой провайдер); локально — Mailpit |
| Подход | Собственный сервис на Go, без внешнего IdP и BaaS |
| Access-токен | JWT, Ed25519 (EdDSA), 15 минут |
| Refresh-токен | Непрозрачный, HMAC-производный, ротация на каждом обновлении, 60 дней со скользящим продлением |
| Хранение | PostgreSQL |
| Удаление аккаунта | Полное (hard delete) |
| Номера | Любые страны (E.164), только мобильные |
| Масштаб | Один экземпляр API; лимиты запросов в памяти |

## 3. Сценарии

### 3.1. Регистрация

1. `POST /v1/auth/register/start {phone}`
   - номер нормализуется в E.164 (регион по умолчанию RU для номеров без `+`); принимаются только валидные номера типа `MOBILE` или `FIXED_LINE_OR_MOBILE` (по `nyaruka/phonenumbers`), иначе `422 validation_failed`;
   - номер уже зарегистрирован → `409 phone_taken`. Это раскрывает факт регистрации номера; осознанный компромисс ради понятного UX, смягчается лимитами;
   - создаётся код `phone_register`, отправляется SMS;
   - ответ `202 {verification_id, expires_in, resend_after}`.
2. `POST /v1/auth/register/verify {verification_id, code}`
   - код верный → помечается использованным, ответ `200 {registration_token, expires_in}`;
   - `registration_token` — JWT с `aud=registration`, `sub=<phone E.164>`, живёт 15 минут. Одноразовость обеспечивает уникальность `users.phone`: после регистрации токен бесполезен.
3. `POST /v1/auth/register {registration_token, password, email, device_name}`
   - если номер успели зарегистрировать после выдачи токена → `409 phone_taken`;
   - в одной транзакции: пользователь и сессия;
   - после коммита выдаётся код `email_verify` и уходит письмо. Если адрес упёрся в лимит отправки или письмо не ушло, ошибка логируется, но регистрацию не ломает (есть повторная отправка);
   - ответ `201 {user, tokens}`, `user.email_verified=false`.

Повторная отправка SMS — повторный вызов `register/start` (новый `verification_id`, старые коды для этого номера аннулируются).

### 3.2. Вход

`POST /v1/auth/login {phone, password, device_name}` → `200 {user, tokens}`.

- Неизвестный номер и неверный пароль дают одинаковый ответ `401 invalid_credentials`. Для неизвестного номера выполняется фиктивная проверка argon2id, чтобы время ответа не выдавало факт регистрации.
- Некорректный формат номера → `422 validation_failed` (формат не раскрывает ничего о пользователях).

### 3.3. Обновление токенов

`POST /v1/auth/refresh {refresh_token}` → `200 {tokens}`. Логика — в разделе 5.3.

### 3.4. Выход

`POST /v1/auth/logout {all_devices?: bool}` (с access-токеном) → `204`. Отзывает текущую сессию или все сессии пользователя. Идемпотентен.

### 3.5. Email

- `POST /v1/me/email/verify {code}` → `200 {user}`. Если этот email уже подтверждён другим аккаунтом → `409 email_taken`.
- `POST /v1/me/email/resend` → `202 {expires_in, resend_after}`; если уже подтверждён → `409 email_already_verified`.
- `PUT /v1/me/email {email, password}` → `202 {user, expires_in, resend_after}`. Смена email требует пароль: иначе украденный access-токен позволил бы сменить email и через сброс пароля захватить аккаунт навсегда. Новый email не подтверждён, на него уходит код. Если передан текущий email: уже подтверждён → `409 email_already_verified`, не подтверждён → работает как повторная отправка кода.

### 3.6. Сброс пароля

1. `POST /v1/auth/password/forgot {email}` → всегда `202 {resend_after}`, независимо от того, есть ли такой подтверждённый email. Код отправляется, только если email подтверждён у какого-то аккаунта и не превышены лимиты по адресу; письмо уходит в фоне, после ответа, чтобы и время ответа не выдавало, есть ли аккаунт.
2. `POST /v1/auth/password/reset {email, code, new_password}` → `204`. Пароль меняется, все сессии пользователя отзываются, клиент заново выполняет вход. Любая ошибка кода (неверный, просроченный, израсходованный, отправленный на прежний адрес) и неизвестный email дают один и тот же ответ `422 invalid_code` без `attempts_left`: по ответу нельзя понять, зарегистрирован ли адрес.

### 3.7. Профиль

- `GET /v1/me` → `200 {user}`.
- `PUT /v1/me/password {old_password, new_password}` → `204`. Остальные сессии отзываются, текущая остаётся.
- `DELETE /v1/me {password}` → `204`. Пользователь удаляется полностью, сессии и коды — каскадом. Требование App Store и Google Play.

Неверный пароль в этих операциях → `403 wrong_password` (не 401, чтобы клиент не принял это за протухший токен и не пошёл обновлять его).

## 5. Токены

### 5.1. Access-токен

JWT, алгоритм EdDSA (Ed25519), заголовок `kid`. Claims: `iss` (из конфига), `aud=api`, `sub=<user_id>`, `sid=<session_id>`, `iat`, `exp` (15 минут).

Проверка в middleware: только алгоритм EdDSA, строгая проверка `iss` и `aud=api` (так registration-токен нельзя использовать как access), допуск по часам 5 секунд. Middleware не ходит в БД: отзыв сессии вступает в силу для access-токена в пределах 15 минут. Чувствительные операции (смена email и пароля, удаление, выход) дополнительно проверяют в БД, что сессия активна.

Приватный ключ — PEM (PKCS#8) из файла `JWT_PRIVATE_KEY_FILE`. Генерация — `go run ./cmd/keygen`.

### 5.2. Registration-токен

Тот же ключ и формат JWT, `aud=registration`, `sub=<phone>`, 15 минут. См. 3.1.

### 5.3. Refresh-токен

Токен детерминированно вычисляется из сессии и номера поколения, поэтому сервер не хранит его вовсе (ни в открытом виде, ни хэшем) и может идемпотентно повторить ответ:

```
mac   = HMAC-SHA256(refresh_key, "refresh:v1" || session_id || generation)
token = base64url(session_id[16] || generation[8, big-endian] || mac[32])
```

`refresh_key` выводится из `APP_SECRET` через HKDF.

Обработка `POST /v1/auth/refresh`:

1. Декодировать; неверная длина, неканоническое написание, поколение меньше 1 или неверный `mac` (сравнение за постоянное время) → `401 invalid_refresh_token`.
2. `SELECT … FOR UPDATE` сессии; не найдена, отозвана или истекла → `401 invalid_refresh_token`. Поколение больше текущего (так бывает после восстановления старого бэкапа БД) → тоже `401 invalid_refresh_token`.
3. `g == session.generation` — штатная ротация: `generation = g+1`, `rotated_at = now`, `expires_at = now + 60 дней`, `last_used_at = now`; вернуть токен поколения `g+1`.
4. `g == session.generation - 1` и `−5 с ≤ now - rotated_at ≤ REFRESH_GRACE` (30 с по умолчанию; нижняя граница — на случай часов, ушедших назад; `REFRESH_GRACE=0` выключает повтор совсем) — повтор в окне (потерянный ответ, параллельные запросы): вернуть тот же токен поколения `session.generation`, ротацию не делать.
5. Иначе (`g` старше) — повторное использование уже израсходованного токена, признак кражи: сессия отзывается (`revoke_reason = refresh_reuse`), событие пишется в лог, ответ `401 refresh_token_reused`.

Access-токен при каждом успешном обновлении выпускается новый.

Ротация `APP_SECRET` делает все refresh-токены недействительными (все пользователи заново выполняют вход).

### 5.4. Сессии

Одна сессия на вход с устройства. Не более 10 активных сессий на пользователя: при создании 11-й отзывается давно не использовавшаяся.

## 6. Коды подтверждения

Один механизм для трёх целей: `phone_register`, `email_verify`, `password_reset`.

- 6 цифр, равномерно из `crypto/rand`.
- В БД хранится `HMAC-SHA256(otp_key, code_id || ":" || code)`. Простой хэш от 6 цифр перебирается мгновенно; привязка к `code_id` не даёт переиспользовать хэш между кодами. `otp_key` выводится из `APP_SECRET` через HKDF.
- Живёт 10 минут. Не более 5 попыток ввода. Попытка списывается в БД атомарно до сравнения кода (`UPDATE … WHERE attempts < 5 … RETURNING`), поэтому параллельные запросы в сумме не получат больше 5 попыток.
- Новый код для той же пары (цель, адресат) аннулирует предыдущие активные. Выдача кода идёт в транзакции под блокировкой адреса (`pg_advisory_xact_lock`), поэтому параллельные запросы не обходят лимиты и не оставляют несколько активных кодов.
- Если доставка не удалась, код удаляется: сбой провайдера не тратит паузу и часовой лимит адреса.
- Поиск кода при проверке: `phone_register` — по `verification_id`; `email_verify` — последний активный код пользователя для его текущего email; `password_reset` — последний активный код пользователя, найденного по подтверждённому email.
- Неверный код → `422 invalid_code` с полем `attempts_left`. Истёк, использован или исчерпаны попытки → `410 code_expired` (нужно запросить новый). Исключение — сброс пароля (раздел 3.6).
- Сравнение — `hmac.Equal`.

Тексты (только русский язык, шаблоны `text/template` встроены в бинарник):

- SMS: `{APP_NAME}: код {code}. Никому его не сообщайте.` + необязательная строка `SMS_APP_HASH` для Android SMS Retriever.
- Письма: простой текст, отдельный шаблон для подтверждения email и для сброса пароля.

### 6.1. Отправка

```go
type SMSSender interface {
    SendSMS(ctx context.Context, phone, text string) error
}
type EmailSender interface {
    SendEmail(ctx context.Context, to, subject, body string) error
}
```

- SMS: реализация `log` (пишет номер и текст в лог). В `APP_ENV=prod` с `SMS_PROVIDER=log` сервер не стартует — иначе коды попадали бы в логи боевого сервера. Реальный провайдер добавляется отдельной реализацией интерфейса (порядок описан в README).
- Email: SMTP через `wneessen/go-mail`. В `prod` запрещён `SMTP_TLS=none`. В dev при пустом `SMTP_HOST` письма вместе с кодами пишутся в лог; в `prod` `SMTP_HOST` обязателен. Отправка письма целиком ограничена 10 секундами (меньше `WriteTimeout` сервера) и прерывается вместе с запросом; сбой или зависание `QUIT` после принятого письма ошибкой не считаются.

## 7. Пароли

- Длина 8–128 символов (Unicode, считается после NFKC — в том виде, в каком пароль хэшируется), без требований к составу (NIST SP 800-63B).
- argon2id: `m=19456 KiB, t=2, p=1`, соль 16 байт, ключ 32 байта, формат PHC (`$argon2id$v=19$m=…,t=…,p=…$salt$hash`). Если параметры в хэше устарели, при успешном входе пароль перехэшируется.
- Пароль перед хэшированием приводится к NFKC (NIST SP 800-63B): один и тот же видимый пароль, набранный на разных клавиатурах, даёт один хэш.
- Параметры argon2id проверяются на границы (t 1–10, p 1–16, m до 256 МиБ, соль 8–64 байта, ключ 16–64) и при старте, и при разборе хранимого хэша; формат хэша разбирается строго.
- Одновременно не более `PASSWORD_HASH_CONCURRENCY` хэширований (по умолчанию 4) — каждое занимает ~19 МБ. Ожидание слота ограничено таймаутом запроса (12 с); не дождались → `503 service_unavailable`.

## 8. Ограничения запросов

Значения по умолчанию, все настраиваются через env.

| Что | Лимит |
|---|---|
| Вход, по IP | 20 в минуту |
| Неудачный вход, по номеру | 5 за 15 минут → `429`; попытка резервируется до проверки пароля и возвращается при успехе, поэтому параллельные запросы не обходят лимит |
| Отправка кода, по адресату (номер/email) | не чаще 1 раза в 60 с и не более 5 в час |
| Отправка кода, по IP | 20 в час |
| Обновление токенов, по IP | 60 в минуту |
| Ввод кода | 5 попыток на код |
| Неверный текущий пароль (смена пароля/email, удаление), по пользователю | как неудачный вход: 5 за 15 минут |

- Лимиты по IP и неудачным входам — в памяти (собственная корзина токенов, `internal/ratelimit`); IPv6-клиенты группируются по /64, счётчики `RATE_*` должны быть положительными, окно неудачных входов — не короче минуты (иначе сервер не стартует); паузу между кодами (`RATE_CODE_COOLDOWN=0`) можно выключить только в dev. Лимиты на отправку кодов по адресату считаются по таблице кодов, переживают перезапуск.
- `429 rate_limited` с заголовком `Retry-After`. Исключение — `password/forgot`: лимит по адресату не раскрывается, ответ всегда `202`.
- IP клиента: `RemoteAddr`; `X-Forwarded-For` учитывается только от адресов из `TRUSTED_PROXIES` (в проде — Caddy), иначе заголовок подделывается.

## 9. Модель данных

```sql
CREATE EXTENSION IF NOT EXISTS citext;

CREATE TABLE users (
    id                uuid PRIMARY KEY,            -- UUIDv7, генерируется в приложении
    phone             text NOT NULL UNIQUE,        -- E.164
    password_hash     text NOT NULL,               -- PHC argon2id
    email             citext NOT NULL,
    email_verified_at timestamptz,
    created_at        timestamptz NOT NULL DEFAULT now(),
    updated_at        timestamptz NOT NULL DEFAULT now()
);
-- email уникален только среди подтверждённых: опечаткой нельзя занять чужой адрес
CREATE UNIQUE INDEX users_verified_email_uq ON users (email) WHERE email_verified_at IS NOT NULL;

CREATE TABLE sessions (
    id            uuid PRIMARY KEY,
    user_id       uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    device_name   text NOT NULL,
    generation    bigint NOT NULL DEFAULT 1,
    rotated_at    timestamptz,
    created_at    timestamptz NOT NULL DEFAULT now(),
    last_used_at  timestamptz NOT NULL DEFAULT now(),
    expires_at    timestamptz NOT NULL,
    revoked_at    timestamptz,
    revoke_reason text
);
CREATE INDEX sessions_user_active_idx ON sessions (user_id) WHERE revoked_at IS NULL;

CREATE TABLE verification_codes (
    id          uuid PRIMARY KEY,
    purpose     text NOT NULL CHECK (purpose IN ('phone_register', 'email_verify', 'password_reset')),
    target      text NOT NULL,                     -- номер E.164 или email в нижнем регистре
    user_id     uuid REFERENCES users(id) ON DELETE CASCADE,
    code_hash   bytea NOT NULL,
    attempts    int NOT NULL DEFAULT 0,
    expires_at  timestamptz NOT NULL,
    consumed_at timestamptz,
    created_at  timestamptz NOT NULL DEFAULT now()
);
-- лимиты отправки считаются по адресату для всех целей сразу
CREATE INDEX verification_codes_target_idx ON verification_codes (target, created_at DESC);
CREATE INDEX verification_codes_user_idx ON verification_codes (user_id, purpose, created_at DESC) WHERE user_id IS NOT NULL;
```

Email нормализуется: обрезка пробелов, нижний регистр, проверка `net/mail.ParseAddress` без display name, длина до 254, локальная часть до 64. Принимаются только ASCII-адреса (Go и citext по-разному приводят не-ASCII к нижнему регистру, а IDN-домен и его punycode дали бы два ключа одного ящика), домен — имя хоста: от двух меток из `a-z0-9-`, без IP-адресов и литералов `[1.2.3.4]`.

Телефон принимается только из ASCII-цифр, `+`, пробелов (в том числе неразрывного) и разделителей `-().`: иначе парсер превращает буквы в цифры (`+7 999 FLOWERS`) и отбрасывает добавочные номера, и SMS ушла бы на чужой номер.

Фоновая очистка раз в час: сессии, отозванные или истёкшие более 30 дней назад; коды старше суток.

## 10. Ошибки

RFC 9457, `Content-Type: application/problem+json`:

```json
{"type": "about:blank", "title": "Validation failed", "status": 422, "code": "validation_failed",
 "errors": [{"field": "password", "code": "too_short"}]}
```

Клиент ориентируется на `code` (стабилен), `title` — для людей и может меняться.

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `bad_request` | Битый JSON, тело больше лимита |
| 401 | `unauthorized` | Нет или невалиден access-токен; пользователь удалён |
| 401 | `invalid_credentials` | Неверный номер или пароль при входе |
| 401 | `invalid_registration_token` | Registration-токен невалиден или истёк |

## 13. HTTP-сервер и эксплуатация

- Таймауты: `ReadHeaderTimeout 5s`, `ReadTimeout 10s`, `WriteTimeout 15s`, `IdleTimeout 60s`.
- Тело запроса — не более 64 КиБ. Неизвестные поля JSON игнорируются: новая версия приложения не должна ломаться о старый сервер.
- Каждый запрос ограничен 12 секундами (меньше `WriteTimeout`, больше лимита SMTP-отправки 10 с).
- Middleware: request ID (`X-Request-ID`), access-лог через slog (без тел запросов), восстановление после паники, авторизация, затем лимиты по IP (анонимные `401` не тратят квоту).
- В логи никогда не попадают пароли, коды (кроме dev: `SMS_PROVIDER=log` и письма при пустом `SMTP_HOST`), токены, `APP_SECRET`.
- При старте сервер до 30 секунд ждёт доступности БД, применяет миграции (под блокировкой: несколько экземпляров могут стартовать одновременно) и только потом открывает порт.
- Graceful shutdown по SIGTERM: до 20 секунд на запросы, затем фоновые письма и очистка; в compose `stop_grace_period: 25s`.
- Образ: многоступенчатая сборка, итоговый — distroless static, пользователь nonroot.

## 15. Тестирование

- Unit: `otp` (генерация, HMAC, попытки, истечение), `token` (подпись, проверка `aud`/`iss`/`alg`, refresh: ротация, окно повтора, обнаружение повторного использования — с подменённым временем), `password`, `contact`, `config` (prod-ограничения).
- Интеграционные: настоящий Postgres через `testcontainers-go`, слой `store` и транзакции.
- Сценарные HTTP-тесты: сервер через `httptest`, настоящая БД, фейковые отправители SMS и email, перехватывающие коды. Сценарии:
  - регистрация целиком → `GET /v1/me`;
  - повторная регистрация номера → `409 phone_taken`;
  - вход: верный и неверный пароль, неизвестный номер, лимит неудачных входов;
  - refresh: ротация, повтор в окне возвращает тот же токен, повтор после окна отзывает сессию;
  - подтверждение email, смена email, конфликт подтверждённого email;
  - сброс пароля: сессии отозваны, старый пароль не работает;
  - смена пароля, выход, выход со всех устройств, удаление аккаунта;
  - коды: неверный, истёкший, исчерпанные попытки, лимиты отправки.
- Smoke: Go-тест с тегом `e2e` против поднятого `docker compose` (адрес из `BASE_URL`).

## 16. Рекомендации мобильному клиенту

- Refresh-токен — только в Keychain (iOS) / Keystore-backed хранилище (Android), не в локальной БД.
- Обновлять access-токен заранее по `access_expires_in` или по `401 unauthorized`; при `invalid_refresh_token` и `refresh_token_reused` — на экран входа.
- Не отправлять параллельно несколько refresh-запросов (сервер переживёт, но это лишняя нагрузка).
- Без сети приложение работает с локальной БД; «вход» офлайн — локальная разблокировка (PIN/биометрия) уже открытой сессии.
- Локальным сущностям — UUIDv7, сгенерированные на устройстве: в фазе 2 они загрузятся на сервер без конфликтов ID.
- Выход без сети: удалить токены локально; серверная сессия истечёт сама.

## 18. Риски

- Без реального SMS-провайдера регистрация в проде не работает (сервер в `prod` с заглушкой не стартует). Нужен адаптер под выбранного провайдера.
- `409 phone_taken` на шаге регистрации раскрывает, зарегистрирован ли номер. Смягчено лимитами.
- Отзыв сессии доходит до access-токена с задержкой до 15 минут (кроме чувствительных операций).
- Лимиты в памяти сбрасываются при перезапуске и не работают при нескольких экземплярах API.
- Любой, кто знает адрес, может запросить код сброса и сжечь его 5 попыток неверным вводом, а также израсходовать лимиты отправки на адрес; ограничено паузой между кодами и часовым лимитом.
- Лимит неудачных входов по номеру может включить посторонний (5 неверных паролей → 15 минут блокировки входа для этого номера). Компромисс ради защиты от подбора.
- Registration-токен одноразов за счёт уникальности номера: если аккаунт удалён в течение 15 минут после регистрации, тот же токен создаст аккаунт заново. Злоумышленник может это проверить, только запросив код, а письмо при этом получит настоящий владелец адреса.

## 19. Уточнения после проверки реализации (2026-10-23)

Весь код планов реализации собран и прогнан до их написания. Изменения относительно первой редакции:

- Сброс пароля для неизвестного email отвечает `410 code_expired` (как известный адрес без активного кода), а не `422 invalid_code`: иначе ответ выдавал бы, зарегистрирован ли адрес.
- При регистрации код подтверждения email выдаётся после коммита, а не в той же транзакции: лимит на адрес не должен срывать регистрацию.
- Интерфейсы отправителей: `SendSMS` и `SendEmail` (один тип может реализовать оба).
- Индексы `verification_codes`: по `(target, created_at)` для лимитов и по `(user_id, purpose, created_at)` для поиска кода пользователя.
- Пакеты: `contact/` вместо `phone/`; добавлены `codes/`, `app/`, `apperr/`, `store/storetest/`, `e2e/`.
- Toolchain Go 1.27.4, `moby/go-archive` v0.3.3 и `klauspost/compress` v1.20.2: закрывают уязвимости, найденные `govulncheck` (по состоянию на 2026-11-14).
- Prod-compose: `deploy/compose.yaml`; Caddy с фиксированным IP, только ему API доверяет `X-Forwarded-For`.
- Сервер при старте ждёт БД до 30 секунд; healthcheck Postgres идёт по TCP (через сокет он отвечает ещё во время initdb).
- Refresh-токен декодируется строго (canonical base64): у токена ровно одно допустимое написание.
- По ревью при выполнении: телефон проверяется по белому списку символов, email — только ASCII, домен — имя хоста, локальная часть до 64 (раздел 9); `Retry-After` у `429` не меньше секунды.
- По ревью: попытка ввода кода списывается атомарно до сравнения (раздел 6) — иначе параллельные запросы обходили лимит в 5 попыток.
- По ревью: refresh-токен принимается только в каноническом написании, поколения меньше 1 отклоняются, окно повтора ограничено с обеих сторон (раздел 5.3); ключ кодека — не короче 32 байт.
- По ревью: попытка входа резервируется атомарно до проверки пароля (раздел 8) — иначе параллельные запросы обходили лимит неудачных входов; IPv6 группируется по /64.
- По ревью: лимитер — собственная корзина токенов вместо `x/time/rate`: возврат попытки через `Reservation.CancelAt` молча не срабатывает, если прошло хоть немного времени, и каждый успешный вход съедал бы попытку.
- По ревью: SMTP-отправка учитывает отмену запроса и ограничена 10 секундами целиком (go-mail применяет контекст только к соединению), а сбой или зависание `QUIT` после принятого письма не превращается в `503` (раздел 6.1). Срок кода в письме — с правильным склонением («1 минуту», «5 минут»).
- По ревью: границы настроек, при которых опечатка тихо ослабляла защиту (раздел 11): `ACCESS_TOKEN_TTL` ≤ 1h, `REFRESH_GRACE` ≤ 5m, `PASSWORD_HASH_CONCURRENCY` ≤ 64, окно неудачных входов ≥ 1m, `TRUSTED_PROXIES` без `/0`, публичный dev-секрет (в любом написании) и нулевая пауза между кодами в prod запрещены, `SMS_APP_HASH` — ровно 11 символов; `Config` не печатает секреты.
- По итоговому ревью части 1: `REFRESH_GRACE=0` выключает повтор полностью (у допуска на сдвиг часов своя константа); длина пароля считается после NFKC; в `APP_NAME` — только печатные символы; вложенные `config.SMTP`, `config.Keys` и `notify.SMTPConfig` тоже печатаются без секретов; `.gitignore` закрывает ключи, дампы и логи.
- По ревью части 2: миграции под сессионной блокировкой goose (параллельный старт нескольких экземпляров падал на `CREATE EXTENSION`); выдача кода под блокировкой адреса, недоставленный код удаляется; вход блокирует строку пользователя (точный лимит сессий, сброс пароля не пропускает новую сессию), повторное хэширование — только если пароль не сменился; `password/forgot` шлёт письмо в фоне, `password/reset` отвечает одним `invalid_code`; лимит на неверный текущий пароль в профиле; таймаут запроса 12 с, авторизация раньше лимитов по IP; порт открывается после миграций.
- По ревью части 3: бэкапы удаляются только после удачного дампа, три последних остаются всегда, healthcheck `backup` показывает сбой; контейнер API только для чтения и без capabilities; Caddy режет тела больше 128 КБ и ставит `nosniff`; `.dockerignore` не пускает секреты в контекст сборки; dev-Postgres и Mailpit только на localhost; CI с минимальными правами, таймаутами и проверкой незакоммиченных сгенерированных файлов; e2e проверяет ротацию refresh и выход со всех устройств; Go 1.27.4 и `klauspost/compress` v1.20.2 — новые уязвимости; встроенная в бинарник OpenAPI-спецификация убрана (тест контракта читает `api/openapi.yaml`).
